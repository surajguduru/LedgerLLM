# Deployment runbook

Production is one Docker container on Render (free web service) plus a Neon Postgres database (free tier).
Everything is configured through environment variables; nothing is baked into the image.

## First deployment

1. **Database (Neon).** Create a project at <https://console.neon.tech>, region close to the Render region.
   Copy the connection string and change the scheme for psycopg 3:
   `postgresql+psycopg://<user>:<password>@<host>/<db>?sslmode=require`.
   Neon is used instead of Render's own Postgres because Render's free database expires after 30 days.
2. **Web service (Render).** New → Blueprint → select this repository. Render reads `render.yaml`. Fill in:
   - `DATABASE_URL` — the Neon string from step 1
   - `LLM_API_KEY` — the Gemini key (<https://aistudio.google.com/apikey>)

   `ADMIN_TOKEN` and `METRICS_TOKEN` are generated by Render; copy them from the service's Environment tab
   (`/metrics` needs `Authorization: Bearer $METRICS_TOKEN`). The health check is `/healthz`, whose `version`
   is the deployed commit. Tables are created on first start (`create_all`).
3. **Seed tenants** from a laptop against the production database:
   ```bash
   DATABASE_URL='<neon string>' .venv/bin/python -m scripts.seed
   ```
   This prints the API keys once and writes them to `.seed_keys.json` (gitignored). Share them out of band;
   never commit them.
4. **Smoke test:** `scripts/demo.sh https://<service>.onrender.com`.

## Admin dashboard (second service)

`ledgerllm-admin` is Grafana with our dashboards baked in (`ops/grafana/Dockerfile`), reading the
production database directly. It is in the same Blueprint, so it deploys alongside the app.

**Why a read replica, not a read-only role.** Neon grants `neon_superuser` to every role it creates,
and the API can neither `REVOKE` it nor set `NOINHERIT` — a role created and granted `SELECT` only
still had INSERT, UPDATE and DELETE on every table (verified 8 Oct). So the datasource points at a
Neon **read-only compute endpoint** instead: writes fail with *"cannot execute INSERT in a read-only
transaction"* at the transaction level, which does not depend on getting GRANTs right.

Create one once, in the Neon console or over the API:

```
endpoint type: read_only     ->  host: ep-<id>-pooler.<region>.aws.neon.tech
role:          grafana_ro    ->  GRANT USAGE ON SCHEMA public, GRANT SELECT ON ALL TABLES
```

Then fill these on the `ledgerllm-admin` service:

| Variable | Value |
|---|---|
| `GRAFANA_DB_HOST` | the **read-replica** pooled host (`-pooler`), no scheme, no port |
| `GRAFANA_DB_USER` | `grafana_ro` |
| `GRAFANA_DB_NAME` | `neondb` (set by the blueprint) |
| `GRAFANA_DB_PASSWORD` | that role's password |
| `GF_SECURITY_ADMIN_PASSWORD` | generated by Render — copy it from the Environment tab to sign in |

`start.sh` refuses to boot without the admin password, because these dashboards show every tenant's
spend and the Render URL is public. Anonymous access is forced off in the image (docker-compose
leaves it on for local convenience — that difference is deliberate).

`PROMETHEUS_URL` stays unset: Prometheus is not deployed, so the image drops the operational
dashboard and its datasource at boot rather than serving a wall of datasource errors. Set it only if
you later point Grafana at a hosted Prometheus.

**Sign in** at `https://ledgerllm-admin.onrender.com` as `admin` with the generated password.

**What it cannot do.** Grafana only reads. Suspend a tenant, revoke or rotate a key, change a plan or
budget — all go through `/admin/*` with the `ADMIN_TOKEN`. That is deliberate: destructive admin
operations are not one click behind a browser session.

## Rolling out a change

| Change | How it ships | How it rolls back |
|---|---|---|
| Code | PR → CI (lint, tests on SQLite and Postgres, red-team gate, summarization gate) → merge to `main` → Render deploys once that commit's checks pass (`autoDeployTrigger: checksPass`) | Render → Deploys → *Redeploy* the previous build |
| Prompt | add `prompts/summarize_vN.yaml`, merge, then set `SUMMARIZE_PROMPT_VERSION=summarize_vN` | set the variable back (Render restarts the service; no build) |
| Guardrail layer | deploy with `GUARDRAILS_MODE=shadow`, read the shadow report, then `enforce` | set `shadow` or `off` |
| Response cache | on by default; TTL per plan in `config/plans.yaml` | `RESPONSE_CACHE_ENABLED=false` |
| Schema | new tables only: `create_all` creates missing tables at start and never alters an existing one, so a new column needs a manual `ALTER TABLE` on Neon before the deploy | old code ignores a column it does not know; a new table can stay |

## Operating notes

- **Cold starts.** The free web service sleeps after 15 minutes without traffic; the first request then waits
  for the container to boot. Send a request to `/healthz` before measuring latency or giving a demo.
- **Connections.** The engine keeps at most 10 connections (`pool_size=5`, `max_overflow=5`) and recycles them
  every 5 minutes, which suits Neon's connection cap and idle suspension.
- **Fallback host.** Hugging Face Spaces (Docker SDK) runs the same image; the container honours `PORT`.
- **Database down.** The pipeline fails closed: no budget reservation means no model call, and the client gets 500.
- **Region.** `render.yaml` pins `region: ohio` to sit next to the Neon database, but Render cannot move an existing
  service: the field applies to services created from the blueprint. A service first created in Oregon stays there
  (about 860 ms of cross-region database round trips per request, README benchmarks) until it is recreated in Ohio.
- **Free-tier quotas.** Gemini's free tier allows 20 `gemini-3.8-flash` requests per project per day, shared by every
  tenant and by the online judge, whose model defaults to `DEFAULT_MODEL`. On free-tier keys set
  `QUALITY_JUDGE_MODEL=gemini-3.5-flash-lite`, and enable the fallback chain (`LLM_FALLBACK_PROVIDER=gemini`,
  `LLM_FALLBACK_MODEL=gemini-3.5-flash-lite`); the blueprint sets neither, so add them in the service's Environment tab.
